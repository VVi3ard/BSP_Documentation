# Ретроспективная спецификация: BSP Documentation

**Статус:** исходная точка для дальнейшей разработки.  
**Дата фиксации:** 12 июля 2026 г.  
**Репозиторий:** `BSP_Documentation` (Codex marketplace).  
**Устанавливаемый plugin:** `bsp-documentation`, версия манифеста `0.1.0`.

Этот документ описывает уже реализованный первый вариант plugin и принятые при его создании решения. Он предназначен для LLM, которая продолжит работу: сначала прочитать этот файл, затем только те исходники, на которые он ссылается. Не нужно заново исследовать весь репозиторий или демо-конфигурацию.

## 1. Назначение

`BSP Documentation` помогает агенту Codex использовать Библиотеку стандартных подсистем (БСП) при разработке 1С/BSL:

1. определить версию БСП целевой конфигурации;
2. обнаружить подходящую подсистему программного интерфейса по задаче;
3. сузить поиск до группы API и прочитать нормативную документацию конкретного метода;
4. найти реальное применение метода в демо-конфигурации той же линии БСП;
5. самостоятельно проследить кодовый сценарий, включая формы, callbacks и клиент-серверные переходы.

Plugin поставляется как единый локальный комплект: skill + stdio MCP + документация HTML + SQLite-векторный индекс + навигационная карта + EDT-демо. Это сознательно не набор независимых MCP и skill.

### Нормативность источников

| Источник | Роль |
| --- | --- |
| Документация БСП | Нормативный источник: ограничения, назначение, параметры и рекомендации метода. |
| Демо-конфигурация | Практический пример потока вызовов. Её нельзя копировать без адаптации и нельзя использовать вместо документации. |
| Навигационная карта | Компактный слой discovery: помогает узнать о существовании подсистемы и группы API до RAG-поиска. |
| SQLite/RAG | Поиск конкретной страницы документации внутри выбранного контекста. |

## 2. Границы и нецели

### Входит в scope

- Версионный поиск документации БСП и чтение полной страницы результата.
- Три уровня сужения контекста: подсистема → группа API → метод.
- Поддержка `development` и `override` режимов поиска.
- Выдача локального каталога bundled EDT-демо для самостоятельного исследования агентом.
- Skill с обязательным маршрутом перед созданием нового BSP-вызова.
- Поставка данных, соответствующих одному manifest версии.

### Не входит в scope текущей версии

- Отдельный RAG/векторный индекс исходников демо.
- «Карточки примеров», автоматически извлечённые сценарии или граф UI-связей по демо.
- MCP-методы, возвращающие готовые фрагменты демо-кода вместо исследования агентом файлов.
- Автоматическая модификация целевого 1С-проекта.
- Поддержка нескольких несопоставленных наборов документации и демо без записи в manifest.
- Поддержка отдельного standalone-MCP как продукта. Внутренний MCP технически может быть запущен отдельно, но проектировать и документировать этот режим специально не нужно.

## 3. Основные пользовательские потоки

### 3.1. Разработка новой функции с БСП

1. Skill активируется для задачи на 1С/BSL, где вероятно использование БСП.
2. Агент вызывает `detect_bsp_version(project_path)`.
3. Для сформулированной задачи вызывает `discover_bsp_api_sections(version, query)`.
4. Для выбранной подсистемы вызывает `get_bsp_api_section_map(version, subsystem)`.
5. Ищет метод только в выбранной группе: `search_bsp(..., mode="development", subsystem, api_group)`.
6. До написания вызова обязательно читает `get_bsp_section(version, section_id)`.
7. Вызывает `get_bsp_demo_location(version)`, делает точный текстовый поиск полного символа в возвращённой EDT-конфигурации.
8. Читает всю содержащую вызов процедуру и прямые зависимости: `ОписаниеОповещения`, вызываемые процедуры, команды формы, BSL-модули формы, `.form`/связанные управляемые формы, серверные переходы.
9. Основной агент принимает решение и адаптирует код под целевой проект.

### 3.2. Extension/переопределение

Маршрут тот же, но в шаге 5 применяется `search_bsp(..., mode="override")`. Документацию callback всё равно нужно прочитать целиком до реализации переопределения.

### 3.3. Известен точный метод

Если точный BSP-символ уже известен, discovery и делегирование не обязательны. Всё равно обязательны: определение версии, `get_bsp_section`, а для нового кода — исследование демо через `get_bsp_demo_location`.

## 4. Политика субагентов и контекста

### Когда делегировать

При неопределённой или многошаговой задаче основной агент может поручить **только** документационный поиск и ранжирование read-only субагенту. Субагент должен вызывать MCP и вернуть компактный результат:

- 3–5 кандидатов API с однострочной причиной;
- рекомендуемый метод и документированные ограничения;
- оставшиеся неопределённости.

Не делегировать простой lookup, если полный метод уже известен. Субагент не меняет целевой проект и не возвращает сырые страницы MCP: это создаёт шум основному потоку.

### Что не делегировать

После выбора метода **основной агент** сам получает расположение демо и исследует его исходники. Полная процедура, callbacks, UI-связи и клиент-серверный поток нужны именно в контексте основного агента, потому что он проектирует адаптацию и пишет код. Нельзя заменять это карточками примеров или вторым MCP-слоем.

### Контекстная дисциплина

Контекст раскрывается прогрессивно:

```text
компактная карта → одна группа API → одна полная страница метода
→ одна процедура демо → только её прямые зависимости
```

Не передавать в LLM технические пути страниц, хэши, счётчики и HTML, если они не нужны текущему шагу. Для демо искать полное имя символа, затем читать процедуру целиком, а не только найденную строку.

## 5. Архитектура и точное размещение данных

```text
BSP_Documentation/
├── .agents/plugins/marketplace.json        # marketplace с одним plugin
├── README.md                                # установка и краткое назначение
├── docs/
│   ├── architecture.md
│   ├── development-workflow.md
│   └── retrospective-spec.md                # этот документ
└── plugins/bsp-documentation/
    ├── .codex-plugin/plugin.json            # manifest plugin
    ├── .mcp.json                            # bundled stdio MCP: bsp_documentation
    ├── skills/bsp-development/SKILL.md      # правила для агента
    ├── scripts/run_bsp_mcp.py               # bootstrap writable runtime
    ├── mcp/bsp-docs-mcp/                    # Python implementation MCP
    │   ├── src/bsp_docs_mcp/
    │   ├── tests/
    │   └── pyproject.toml
    └── data/
        ├── manifest.json                    # единственный источник сопоставления версий и SHA-256
        ├── indexes/<family>/index.sqlite    # read-only индекс документации
        ├── packages/*-src.zip               # исходники демо без бинарных внешних компонент
        ├── navigation/<version>/program-interface.json
        ├── sources/<version>/               # исходные HTML БСП
        └── demo/<demo-version>/             # bundled EDT проект
```

`plugin.json` регистрирует `skills: "./skills/"` и `mcpServers: "./.mcp.json"`. `.mcp.json` запускает `python scripts/run_bsp_mcp.py` с `cwd: "."`; поэтому runner и данные должны оставаться внутри корня plugin.

### Версионное соответствие

Текущий `plugins/bsp-documentation/data/manifest.json` определяет единственную поддерживаемую связку и архив демо. При первом обращении архив распаковывается в `%CODEX_HOME%\bsp\<demo_version>\src`; установленная cachebuster-версия plugin в этот путь не входит.

| Слой | Версия |
| --- | --- |
| Документация | `3.1.11` |
| Навигационная карта | `3.1.11` |
| Семейство SQLite-индекса | `3.1` |
| EDT-демо | `3.1.11.115` |
| Формат демо | `1c-edt` |

Правило совместимости поиска — major.minor family: полный номер `3.1.11.155` использует индекс `3.1`. Для демо сервер выбирает точное совпадение, затем релиз `3.1.11`, затем самый новый каталог с префиксом `3.1.11.`. При добавлении версии нужно обновлять **все** соответствующие данные и manifest вместе; не полагаться на одно только правило поиска каталогов.

## 6. Runtime и bootstrap

Runner `scripts/run_bsp_mcp.py` — единственная точка запуска поставляемого MCP.

- При первом старте он создаёт виртуальное окружение в `%LOCALAPPDATA%\\BSP_Documentation\\venv`.
- Переопределение: `BSP_DOCUMENTATION_RUNTIME_DIR`.
- В venv устанавливается локальный пакет из `mcp/bsp-docs-mcp`.
- Перед запуском runner устанавливает `BSP_DOCS_DATA_DIR=<plugin-root>/data`.
- Исходники plugin, HTML, SQLite и демо считаются read-only; зависимости и временные данные не должны записываться в каталог установленного plugin.

Семантический поиск использует OpenRouter:

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `OPENROUTER_API_KEY` | Runtime-секрет, требуется для `search_bsp`; plugin передаёт его через `env_vars` | нет |
| `OPENROUTER_BASE_URL` | Параметр сборки/ручного запуска MCP; установленный plugin его не пробрасывает | `https://openrouter.ai/api/v1` |
| `BSP_EMBEDDING_MODEL` | Параметр сборки индекса; не является свободной runtime-настройкой готового plugin | `qwen/qwen3-embedding-8b` |

Ключ хранится только в пользовательском окружении и не должен попадать в Git или plugin. После установки или замены ключа пользователь полностью перезапускает Codex, поскольку stdio MCP наследует окружение при запуске.

Навигация, список версий, получение секции по id и путь к демо не требуют ключа OpenRouter. Ошибка отсутствующего или недействительного ключа допустима только при семантическом поиске и должна быть понятной пользователю.

### Инвариант embedding-модели

- При сборке индексатор записывает `embedder.model` в SQLite metadata под ключом `model`.
- При поиске `SearchEngine` обязан точным строковым сравнением проверить, что runtime-модель совпадает с metadata индекса, до обращения к dense retrieval.
- Размерность query embedding дополнительно проверяется перед умножением векторов, но совпадение размерности само по себе не доказывает совместимость embedding-пространств.
- Поставляемый индекс линии 3.1 построен моделью `qwen/qwen3-embedding-8b`.
- Изменение модели, provider endpoint или несовместимое изменение preprocessing требует полной переиндексации корпуса и поставки нового согласованного `index.sqlite`. Нельзя переключить только `BSP_EMBEDDING_MODEL` у готового индекса.
- Перед первым семантическим поиском в процессе выполняются пять контрольных paraphrase-запросов. Пять canary и реальный пользовательский запрос эмбеддятся одним batch; ожидаемый section id каждого canary должен находиться в top-8.
- Canary не используют сохранённые query embeddings: иначе смена внешней ревизии модели под прежним id осталась бы незаметной.
- Успешная проверка действует 24 часа и повторяется при изменении runtime model либо build metadata индекса. Состояние хранится в памяти процесса и сбрасывается при перезапуске MCP.
- Ошибка canary блокирует выдачу результатов: правдоподобный, но потенциально несовместимый рейтинг не должен передаваться агенту как достоверный.

## 7. Контракт MCP

Сервер называется `bsp_documentation`; реализация — `mcp/bsp-docs-mcp/src/bsp_docs_mcp/server.py`. Инструкции сервера и skill намеренно повторяют обязательный маршрут, чтобы агент знал о навигации до того, как попытается писать код.

| Инструмент | Вход | Назначение и существенный результат |
| --- | --- | --- |
| `detect_bsp_version` | `project_path="."` | Ищет `Configuration.distr`, затем `ParentConfigurations.bin`; возвращает `full_version`, `index_family`. |
| `list_bsp_versions` | — | Возвращает установленные семейства индексов. |
| `list_bsp_api_sections` | `version` | Полный компактный перечень подсистем программного интерфейса данной версии. |
| `discover_bsp_api_sections` | `version`, `query`, `limit=5` | Ранжирует подсистемы по названиям, описаниям и ключевым словам навигационной карты. |
| `get_bsp_api_section_map` | `version`, `subsystem` | Возвращает одну подсистему и компактные группы: имя, описание, `interface_kind`; не возвращает список всех методов. |
| `search_bsp` | `version`, `query`, `limit=8`, `mode="all"`, `subsystem?`, `api_group?` | Семантический поиск по SQLite/RAG; режимы: `all`, `development`, `override`, `subsystem`. Для разработки после карты ожидаются `development + subsystem + api_group`. |
| `get_bsp_section` | `version`, `section_id` | Полный текст выбранной документационной секции. Обязателен перед новым BSP-вызовом. |
| `get_bsp_source_section` | `version`, `section_id`, `format="markdown"` | Оригинальная исходная страница Markdown/HTML; использовать только при реальной необходимости, не как обычный путь. |
| `get_bsp_demo_location` | `version` | Проверяет и лениво распаковывает архив, возвращает `requested_version`, `available`, а при успехе — `demo_version`, стабильный абсолютный `demo_root=%CODEX_HOME%\bsp\<версия>\src`, `source_format="1c-edt"`, `usage_hint`. Агент сам ищет по `demo_root`; MCP не выдаёт карточки/кодовые срезы. |

Особенность `get_bsp_demo_location`: метод сначала проверяет доступность соответствующего индексного семейства. Это защищает от случайного выбора демо для неподдерживаемой версии. При отсутствии кандидата он возвращает `available: false` и причину, а не выдумывает путь.

## 8. Принятые решения и причины

| Решение | Причина |
| --- | --- |
| Отдельный repository `BSP_Documentation`, а не преобразование старого MCP-repo | Plugin — самостоятельная единица распространения с skill, MCP и большими данными; исходный MCP остаётся внутренним компонентом. |
| Marketplace с одним plugin | Установка даёт согласованный набор компонентов и версий одной операцией. |
| Демо включено в plugin | Агенту не требуется знать внешний путь или иметь копию демо в целевом проекте. Поставляемая версия — `3.1.11.115` из EDT-исходников. |
| Демо исследуется обычным файловым поиском | Нужен не только вызов метода, но и полный сценарий: UI, формы, callback, клиент-сервер. Дополнительный RAG/карточки неизбежно теряли бы связи или раздували контекст. |
| MCP сообщает стабильный `demo_root`, а не возвращает примеры | Основной агент получает свободу исследовать реальные файлы именно тогда, когда метод уже выбран; путь не ломается после обновления plugin. |
| Субагент ранжирует только документационные кандидаты | Это уменьшает шум у основного агента, но не отнимает у него необходимый для реализации контекст демо. |
| Карта API строится отдельно от RAG | Проблема была не только в качестве поиска: LLM не знает о существовании API до запроса. Карта создаёт слой discovery без загрузки тысяч методов в контекст. |
| Семантическое обогащение карты выполняется локальным Codex, не OpenRouter | OpenRouter остаётся зависимостью только retrieval embeddings. Обогащение — офлайн-процесс сборки, с контролем и валидацией результата. |
| Поставляемые данные read-only, runtime вне plugin | Установленный plugin должен быть воспроизводимым и не требовать записи в Git-каталог. |
| Поддержка standalone MCP не является целью | Качество продукта измеряется работой plugin; не расходовать ресурс на отдельную установку/документацию режима MCP. Техническая совместимость не запрещена. |

## 9. Установка, публикация и права

### Установка для пользователя

```powershell
codex plugin marketplace add VVi3ard/BSP_Documentation --ref main
codex plugin add bsp-documentation@bsp-documentation
```

Затем включить **BSP Documentation** в Codex и начать новую задачу. Нужны Codex с поддержкой plugins, Python 3.11+ и сеть при первом запуске для установки Python-зависимостей в личный runtime.

### Публикация

- Целевой GitHub-репозиторий публичный: `VVi3ard/BSP_Documentation`.
- До коммита проверить размер данных и лимиты GitHub; текущая поставка велика из-за HTML и EDT-демо.
- Если будущие версии превышают лимиты GitHub либо изменяются как большие бинарные объекты, выбрать Git LFS или release assets, но не ломать целостность manifest и установки plugin.
- Не публиковать ключи OpenRouter, локальные venv, кэш или абсолютные пользовательские пути.
- Документация и демо БСП могут иметь лицензионные ограничения 1С. Публичность repository не является подтверждением права на перераспространение: перед каждым расширением/релизом отдельно проверять применимые условия.

## 10. Известные свидетельства валидации и ограничения

### Что есть в исходниках

- Внутренний MCP содержит 12 test-модулей: corpus, crawler, embeddings, exporter, indexer, installer, navigation, parser, search, server, storage, versions.
- В `test_server.py` и `test_versions.py` есть проверки детектирования версии; навигация и сервер имеют выделенные тестовые модули.
- В коде `get_bsp_demo_location` реализованы успех, отсутствие демо и выбор совместимого префикса версии.
- Plugin имеет корректно разделённые manifest, `.mcp.json`, runner, skill и data manifest; runner не использует зашитый абсолютный путь данных.

### Что не следует считать доказанным только по этой спецификации

- Этот ретроспективный spec не запускает тесты и не заменяет проверку после будущих изменений.
- В Git-рабочем дереве на момент фиксации нет исходного commit; проект находится на ветке `codex/bsp-documentation` и файлы staged для первой публикации. Перед публикацией проверить `git status`, фактический remote и результаты установки на чистой машине/в чистом Codex.
- Семантический поиск зависит от доступности OpenRouter и качества embeddings; fallback без ключа для `search_bsp` сейчас не заявлен.
- Точное совпадение строкового идентификатора модели защищает от случайной подмены модели, но не фиксирует ревизию внешней модели у провайдера. Для полностью воспроизводимой пересборки в будущем следует сохранять provider, revision, preprocessing contract и объявленную размерность как build metadata.
- Есть один набор данных 3.1.11/3.1.11.115; поведение для других линий не должно обещаться до добавления полного согласованного набора.
- `get_bsp_demo_location` возвращает путь в локальном `%CODEX_HOME%`. В удалённом/контейнерном размещении файловое пространство MCP и агента может различаться; для такого режима потребовался бы отдельный серверный read/search fallback, которого сейчас нет.
