# Хук bsp-first: спецификация

Статус: описание для реализации. Кода хука в комплекте нет. Есть данные (`hook/data/`),
образцы алгоритмов (`scripts/check_antipatterns.py`, `scripts/similar_names_probe.py`)
и замеры на коде АСПУ.

## 1. Зачем

Навык помогает, только если модель его открыла. Модель, которая не знает о методе БСП,
не станет его искать. Хук закрывает этот разрыв: в момент записи BSL он смотрит на
**добавляемый** код и возвращает модели подсказку, какой метод БСП или платформы уже
решает задачу. Модель получает подсказку сразу после записи и может исправить код в том же ходе.

Не цели:
- не линтер и не замена EDT/BSL LS: стиль, типы, ошибки не проверяются;
- не блокирует работу (кроме опционального строгого режима, раздел 8);
- не оценивает существующий код: только то, что модель добавляет сейчас.

## 2. Принципы

| Принцип | Требование |
|---|---|
| Неблокирующий | Выход 0, JSON с `additionalContext`. Без `permissionDecision`. |
| Fail-open | Любая ошибка хука (нет данных, битый JSON, исключение) - выход 0 без вывода. Ошибка пишется в лог хука. |
| Только добавленное | Проверяются строки, которых не было в файле до правки (раздел 4). |
| Быстрый | Не больше 300 мс на вызов на файле 10 000 строк. Регулярные выражения компилируются один раз. |
| Без сети и LLM | Только локальные JSON из `hook/data` и `skill/bsp-first/data`. |
| Короткий вывод | Не больше 8 подсказок и 1500 символов. Остальное - строкой «ещё N подсказок». |
| Без маркеров в коде | Подавление только конфигом хука (раздел 7). Комментарии-исключения в BSL не вводить: в проекте запрещены механизмы подавления диагностик в коде. |

## 3. Где подключается

### Claude Code

Событие `PreToolUse`, неблокирующий ответ с `additionalContext`. Протокол сверен с
документацией хуков Claude Code (code.claude.com/docs/en/hooks) на 2026-09.
При реализации сверить ещё раз.

`.claude/settings.json` проекта:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit|mcp__EDTMCPServer__write_module_source",
        "hooks": [
          {
            "type": "command",
            "command": "python \"${CLAUDE_PROJECT_DIR}/.claude/hooks/bsp_first_hook.py\"",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

- Точное имя MCP-инструмента записи модуля EDT сверить локально (`/mcp` или лог хука):
  формат `mcp__<сервер>__<инструмент>`.
- Для `Write`/`Edit`/`MultiEdit` хук сам отфильтровывает файлы не `*.bsl` (выход 0 без вывода).
- Почему `PreToolUse`, а не `PostToolUse`: до записи на диске еще старая версия файла,
  поэтому добавленные строки находятся простым сравнением без хранения состояния.

Ответ хука (stdout, выход 0):

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "additionalContext": "bsp-first: в добавляемом коде есть задачи, которые уже решает БСП ..."
  }
}
```

### Codex

Проектные хуки Codex подключать по документации своей версии Codex. Ядро хука
(разделы 4-6) не зависит от агента: вход - путь файла, старый и новый текст; выход - список
подсказок. Реализовать ядро отдельной функцией, а адаптеры Claude Code и Codex - тонкими
обертками. Если хуков в Codex нет - запускать ядро как проверку перед коммитом (раздел 9).

## 4. Вход: что считать добавленным кодом

Хук получает на stdin JSON: `tool_name`, `tool_input`, `cwd`, `session_id`.

| Инструмент | Путь | Старый текст | Новый текст |
|---|---|---|---|
| `Write` | `tool_input.file_path` | файл на диске (пусто, если нет) | `tool_input.content` |
| `Edit` | `tool_input.file_path` | `tool_input.old_string` | `tool_input.new_string` |
| `MultiEdit` | `tool_input.file_path` | все `edits[].old_string` | все `edits[].new_string` |
| write_module_source (EDT) | путь модуля из параметров, приведенный к `Configuration/src/...` | модуль на диске или фрагмент, который заменяется, если инструмент принимает имя метода | исходный текст из параметров |

Параметры инструмента EDT посмотреть в его схеме: какой в нем путь модуля и пишется ли
модуль целиком или один метод.

Добавленный код - строки нового текста, которых нет в старом (`difflib.SequenceMatcher`,
опкоды `insert`/`replace`). Для правил на несколько строк (AP02-AP04, AP16, AP23) проверяется
окно: добавленные строки плюс 15 строк контекста до и после из нового текста.
Совпадение засчитывается, только если хотя бы часть совпавшего фрагмента лежит в
добавленных строках.

Для определения контекста (раздел 5) нужен весь новый текст модуля. Для `Edit` это файл
на диске с примененной заменой `old_string -> new_string`.

## 5. Контекст исполнения

Правило срабатывает, только если его поле `context` совпадает с контекстом кода:
`any` - всегда; `client` / `server` - на клиенте / сервере; код `both` проходит любое правило.

Как определить контекст для позиции в модуле (образец - `context_at` в
`scripts/check_antipatterns.py`):

1. Найти ближайшее объявление `Процедура`/`Функция` выше позиции. Если строка перед ним -
   директива компиляции: `&НаКлиенте` -> client; `&НаСервере`, `&НаСервереБезКонтекста` ->
   server; `&НаКлиентеНаСервере...` -> both.
2. Иначе по модулю. Общий модуль с суффиксом `КлиентСервер` -> both; `Клиент`,
   `КлиентГлобальный` -> client; прочие общие модули -> server. Модуль команды -> client.
   Модули объектов, менеджеров, наборов записей -> server.

Точнее - флаги из `<Модуль>.mdo` (`server`, `clientManagedApplication`); суффиксное правило -
соглашение БСП, его хватает на практике.

## 6. Проверки

Выполняются по порядку, все подсказки сливаются в один ответ.

### A. Антипаттерны (`hook/data/antipatterns.json`)

25 правил: регулярное выражение, контекст, уверенность, что предложить, короткое «почему»,
примеры `bad`/`good`. Флаги `IGNORECASE | MULTILINE`, синтаксис Python `re`.
Формулировка подсказки зависит от уверенности:

- `high` - «Используй X вместо ...»;
- `medium` - «Проверь, не подходит ли X ...»;
- `low` - показывать, только если подсказок уровня high/medium меньше трех.

Исходник правил - `scripts/antipatterns_source.py`; JSON из него генерируется, руками JSON не править.

### B. Вызов устаревшего метода БСП (`hook/data/bsp-deprecated.json`)

В добавленном коде искать вызовы `Модуль.Метод(` по регулярному выражению
`(?<![\wА-Яа-яЁё.])(Модуль)\.(Метод)\s*\(`. Совпадение с `call` из файла -> подсказка
с текстом `note` (в нем БСП указывает замену). Уверенность high.

### C. Вызов служебного API БСП (`hook/data/bsp-internal.json`)

То же для методов модулей `*Служебный*` и областей `СлужебныйПрограммныйИнтерфейс` /
`СлужебныеПроцедурыИФункции`. Подсказка: «служебный API БСП не контракт и может
измениться при обновлении; найди публичный аналог в навыке bsp-first».
Не срабатывает, если правка идет в объект самой БСП (раздел 7, исключение путей).

### D. Новый метод похож на метод БСП

Для каждого нового объявления `Процедура`/`Функция` в добавленных строках (образец -
`scripts/similar_names_probe.py`):

1. Пропустить обработчики событий: имя начинается с `При`, `Перед`, `После`, `Обработка`,
   `Подключаемый_`, `Начало`, `Окончание` + заглавная буква.
2. Разбить имя на слова по заглавным буквам, каждое слово обрезать до 5 букв (основа).
   Убрать стоп-основы (список в скрипте).
3. Кандидаты - методы из `skill/bsp-first/data/article-methods.json` со статусом `ok`
   (около 400 популярных методов общего назначения). Весь индекс не использовать: шума
   втрое больше (замер в разделе 10).
4. Совпадение: не меньше 2 общих основ и доля общих основ от основ нового имени не меньше 0,67.
5. Выдать до 3 кандидатов, сортировка по доле совпадения, затем по популярности (`calls`).
   Уверенность medium: «Перед тем как писать X, проверь Y».

## 7. Исключения и настройка

Файл `hook/config.json` (создать при реализации):

```json
{
  "enabled": true,
  "mode": "hint",
  "disabled_rules": [],
  "exclude_paths": ["Tests/**", "xUnitForEDT/**", "**/DataProcessors/КонсольЗапросов*/**"],
  "bsp_objects_file": "hook/data/bsp-objects.txt",
  "max_hints": 8,
  "max_chars": 1500
}
```

- `exclude_paths` - glob от корня репозитория. Тестам разрешено писать что угодно.
- `bsp_objects_file` - список объектов БСП в целевой конфигурации (`CommonModules/ОбщегоНазначения`
  и т.п.). В объектах самой БСП хук молчит: правки в них - отдельная история.
  Список строится один раз при обновлении БСП: объекты, которые есть в поставке БСП нужной
  версии (так отделялся прикладной код для замеров в разделе 10).
- Правило отключается целиком по `id`. Точечного подавления в коде нет (раздел 2).

Повторы. Одна и та же подсказка (правило + файл + вызов) выдается один раз за сессию.
Состояние - файл `<temp>/bsp-first-<session_id>.json`, удалять его не нужно.

## 8. Режимы

- `hint` (по умолчанию) - только `additionalContext`.
- `strict` (опционально, включать после обкатки) - для уверенности high в проверках A и B
  первая попытка отклоняется: `permissionDecision: "deny"` с текстом подсказки в
  `permissionDecisionReason`. Повтор той же правки (тот же хеш `tool_input`) пропускается,
  чтобы модель могла осознанно оставить свой вариант. Хеш хранится в файле состояния сессии.

## 9. Запуск без агента

Ядро с CLI: `python bsp_first_hook.py --check <файл.bsl> [--base <git-ref>]`.
Сравнение с версией из git вместо старого текста. Годится для pre-commit, CI и Codex без хуков.
Выход 0 всегда; подсказки печатаются в stdout.

## 11. Тест-план реализации

1. `python scripts/check_antipatterns.py hook/data/antipatterns.json skill/bsp-first/data/bsp-api-index.json`
   - все `bad` срабатывают, `good` молчат, методы из `suggest` существуют.
2. Юнит-тесты ядра:
   - `Write` нового файла с `bad`-примером -> подсказка;
   - `Edit`, где `bad` есть только в `old_string` -> тишина (код удаляется, не добавляется);
   - `Edit` в файле, где `bad` уже есть в другом месте -> тишина;
   - AP25 в `&НаСервере` -> тишина, в `&НаКлиенте` -> подсказка;
   - вызов `ОбщегоНазначенияКлиентСервер.КодОсновногоЯзыка(` -> проверка B;
   - `Процедура ПриЗаписи(Отказ)` -> тишина; `Функция ДобавитьСообщениеДляЖурнала(...)` -> проверка D;
   - путь из `exclude_paths` -> тишина; не `.bsl` -> тишина;
   - битый stdin -> выход 0 без вывода;
   - повтор той же подсказки в сессии -> тишина.
3. Производительность: `Write` модуля 10 000 строк < 300 мс.
4. Обкатка: неделя в режиме `hint`, собрать лог срабатываний (правило, файл, принята ли
   подсказка - по следующей правке), отключить или ослабить шумные правила, потом решать про `strict`.

## 12. Сопровождение

- Обновление БСП: пересобрать данные по `README.md` комплекта из исходников **целевой**
  конфигурации - тогда индекс точно совпадает с версией БСП проекта.
- Новое правило: добавить в `scripts/antipatterns_source.py` с `bad`/`good`, сгенерировать
  JSON, прогнать проверку и замер на коде проекта.
- Шумное правило: сначала сузить регулярное выражение и добавить `good`-пример на ложное
  срабатывание, отключать - в последнюю очередь.
